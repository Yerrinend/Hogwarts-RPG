# Память и контрольное сохранение

На постоянном Windows-диске: `python scripts/windows_entry.py batch-start --durable-local` один раз перед пакетом. На Linux/Cloud пакетное начало заблокировано. Там остаются `start` / `save --chapter N` с публикацией каждой главы: долговечность неопубликованной задачи не подтверждена. Пакетный режим не переносит локальный журнал на телефон до checkpoint.

## После главы

Агент создаёт `.local/entry.json`, затем вызывает `python scripts/windows_entry.py record --entry .local/entry.json`. Входной JSON:

- `scene_details`: компактная, но содержательная запись сцены: действия, обстановка и эмоциональные реакции, важные для продолжения; существенные диалоги сохранять в dialogues. Сохранить значимые подробности и причинность, не перепечатывать всю главу.
- `chapter` и `state_patch`: предпочтительный компактный ввод. В state_patch перечислить только изменившиеся поля в формате `{"path":["chapter"],"value":276}` (номер в примере условный; фактический должен быть следующим). Другой пример пути — `["tables","Имя таблицы",1,2]`. Скрипт сам сохраняет полный точный снимок `state_after`, наследуя неизменившиеся поля предыдущего состояния. Пропущенное изменение останется старым, поэтому включать все фактические изменения, дату/время, место и доступные действия.
- Вместо chapter/state_patch можно передать полный `state_after` в формате существующего state.json. Не передавать оба способа одновременно. Это резервный ввод при изменении структуры; для обычного хода использовать патч. Нельзя угадывать числа или менять неизменившиеся характеристики.
- `quick_save`: краткое текущее состояние с римским номером, временем, местом, последним решением и доступным выбором.
- Списки `events`, `dialogues`, `decisions`, `promises`, `secrets`, `npc_knowledge`, `npc_development`, `open_threads`: конкретные факты с участниками, мотивами и последствиями; в знаниях — кто, от кого и что узнал. Отсутствующее новое событие обозначать `[]`. Значимые формулировки обещаний и признаний сохранять точно.
- `memory_targets`: имена затронутых сводок из character_canon.md, relationship_history.md, future_plans.md, inventory.md. Новые обещания/линии требуют future_plans.md; развитие NPC — character_canon.md. Изменение отношений, важный диалог, конфликт, примирение или знание записывать в нужную сводку, даже без изменения очков.
- `stat_deltas`: по одной записи на каждую изменившуюся ячейку четырёх таблиц. Поля `path` (ключ таблицы, индекс строки, индекс столбца; индексы с нуля), `before`, `after`, численный `delta` со знаком и `reason`. При отсутствии изменений `[]`. Для изменения оформления без изменения числа — delta 0. Не угадывать перевод уровней в баллы: применять установленную механику. Для всех изменённых таблиц требуется review relationship_history.md; это консервативное требование, а не утверждение об изменении отношений.

Образец структуры одной дельты (условный технический пример):

```json
{"path":["Имя таблицы",1,2],"before":"10","after":"12","delta":2,"reason":"конкретный подтверждённый поступок"}
```

Служебные хеши, цепочку, происхождение и общий список изменений состояния добавляет скрипт. Запись устанавливается атомарно без перезаписи, содержимое сбрасывается на диск; вторая копия находится в `.local/journal-recovery/`. Это две копии на одном диске, не защита от потери диска. Если файловая система не поддерживает безопасную установку записи, record завершается ошибкой: не продолжать без надёжного сохранения.

Record не вызывает Git или сеть. Он проверяет только текущий пакет (максимум 10 записей) и входные числа/цепочку; это машинное чтение, не повторная загрузка глав в контекст модели. На 10-й записи требуется checkpoint, 11-я блокируется. Чат используется непосредственно, пока последние главы доступны; после сжатия/потери контекста читать только необходимые записи. Старые главы и архив не перечитывать.

## Контрольное сохранение

По достижении 10 глав или по «сохрани», «заканчиваем», «перехожу на другое устройство»:

1. Восстановить финальные state.json и quick_save.md из последнего снимка; актуализировать current_save.md и current_stats.md.
2. Дополнить campaign_log.md и full_timeline.md каждой главой пакета (номер, дата, действие, последствия). Обновить указанные memory_targets; не терять существенные сцены, секреты и источники знаний. Скрипт проверяет наличие изменений файлов и номеров глав, но смысловую полноту обязан проверять агент.
3. Выполнить `python scripts/windows_entry.py checkpoint`. Проверяются цепочка и резервная копия, точное совпадение финального состояния, диапазон, основа main и обязательные сводки. Один коммит публикует 1–10 глав. Git проверяется на границах пакета, а не на каждом record.
4. При подтверждённом main сообщить только «💾 Прогресс сохранён — главы X–Y.». При ошибке не сообщать успех; сохранить все записи и объяснить блокировку. Уже созданный коммит повторно публикуется через `publish`, без второй главы/коммита.

При неполном переносе сводок checkpoint останавливается до коммита. При потере процесса журнал и отметка пакета остаются: перечитать отметку, проверить обе копии, продолжить пакет либо checkpoint. Если primary потерян, повторить record с тем же входом: одинаковая fsync-копия восстановит запись; несовпадение требует ручной проверки. Не удалять active-turn.json или sync.lock вслепую. При потере только маркера восстановление требует проверки исходного коммита по журналу, а не начала нового пакета.

Успешно опубликованные журналы сохраняются в Git как долгосрочные свидетельства. Предыдущие записи не редактировать и не удалять. Несохранённый пакет блокирует logon pull. Удалённые изменения за время пакета блокируют публикацию, но не уничтожают локальную версию. Не играть одновременно на двух устройствах.

Изменения AGENTS/скриптов — технический коммит без продвижения главы. Это не повод писать сообщение о сохранении вымышленных глав.
